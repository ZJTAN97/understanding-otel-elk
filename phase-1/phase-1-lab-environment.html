Phase 01 · Lab environment

A cluster pinned to 1.28.15

Three k3s nodes in Docker that behave like the production cluster — so every compatibility finding in the next twenty phases actually transfers.

Done when: three Ready nodes on v1.28.15, a kubectl within one minor of them, and the cluster definition living in phase-1/k3d/cluster.yaml instead of your shell history.

Why skew bites

kubectl supports ±1 minor from the API server. At 6 minors it mostly works, which is exactly the problem: it drops or mangles fields on API objects it doesn't know, and ECK manifests are full of them. You get a resource that applied cleanly and does the wrong thing.

What you are building

Run it

01

Replace kubectl with a 1.29 build

Five minutes, and it removes a whole class of confusing failures before they happen. Put it somewhere early on PATH; keep the new one out of System32.

PowerShell
New-Item -ItemType Directory -Force "$env:USERPROFILE\bin" | Out-Null
curl.exe -Lo "$env:USERPROFILE\bin\kubectl.exe" `
  https://dl.k8s.io/release/v1.29.15/bin/windows/amd64/kubectl.exe

# prepend to PATH for this session, then persist it
$env:PATH = "$env:USERPROFILE\bin;$env:PATH"
[Environment]::SetEnvironmentVariable(
  "PATH", "$env:USERPROFILE\bin;" + [Environment]::GetEnvironmentVariable("PATH","User"), "User")

kubectl version --client   # expect: Client Version: v1.29.15
If it still says v1.34.1

Docker Desktop ships its own kubectl and puts it early on the machine PATH. Check with Get-Command kubectl -All and make sure ~\bin wins, or open a fresh terminal.

02

Write the cluster definition to a file

The flags-in-shell-history version works. Putting it in git is the entire habit this phase is teaching, so start as you mean to continue.

phase-1/k3d/cluster.yaml
apiVersion: k3d.io/v1alpha5
kind: Simple
metadata:
  name: elastic-lab
# Pinned to match production. Do not float this tag.
image: rancher/k3s:v1.28.15-k3s1
servers: 1
agents: 2
# Without this, k3d writes host.docker.internal + a random port into the
# kubeconfig, and on Docker Desktop + WSL2 that name resolves to a vEthernet
# address the host cannot reach. Pin to loopback and a fixed port.
kubeAPI:
  host: "127.0.0.1"
  hostIP: "127.0.0.1"
  hostPort: "6445"
options:
  k3d:
    wait: true
    timeout: "300s"
  kubeconfig:
    updateDefaultKubeconfig: true
    switchCurrentContext: true
PowerShell · from the repo root
New-Item -ItemType Directory -Force phase-1\k3d | Out-Null
# paste the YAML above into phase-1\k3d\cluster.yaml, then:
git add phase-1\k3d\cluster.yaml
03

Create the cluster

PowerShell
k3d cluster create --config phase-1\k3d\cluster.yaml
If kubectl now times out — hit on this machine

The symptom is couldn't get current server API group list: Get "https://host.docker.internal:56304/api": dial tcp 172.23.142.3:56304: connectex: A connection attempt failed..., repeating every ~20 seconds. The cluster is fine — docker ps shows serverlb publishing 0.0.0.0:56304->6443/tcp and k3d cluster list reads 1/1, 2/2. Only the kubeconfig is wrong.

k3d detects Docker Desktop and writes host.docker.internal as the API server host. With the WSL2 backend that name resolves to a vEthernet address (172.23.142.3 here) that the Windows host cannot route to — and if your DNS is a corporate resolver, it may not resolve at all. Loopback works, because the port is published on 0.0.0.0. Prove it, then rewrite the one field:

PowerShell
docker ps --filter name=k3d-elastic-lab-serverlb --format "{{.Ports}}"
# 0.0.0.0:56304->6443/tcp   → take the host port

curl.exe -sk -o NUL -w "%{http_code}`n" https://127.0.0.1:56304/version
# 401 is the success case here: TLS and HTTP work, curl just has no credentials

kubectl config set-cluster k3d-elastic-lab --server=https://127.0.0.1:56304

The kubeAPI block in step 2 makes this stick across recreates, and fixes the port at 6445 so the URL stops changing. Recreating the cluster with a config file that lacks it puts the broken host back.

First run pulls rancher/k3s:v1.28.15-k3s1 three times over — one image, three containers — so expect a few minutes. The equivalent one-liner, if you want to see what the file is doing:

k3d cluster create elastic-lab `
  --image rancher/k3s:v1.28.15-k3s1 `
  --servers 1 --agents 2

05

The deliberate exercise

Look at what k3d cluster create gave you that you never asked for, and decide for each one whether production has an equivalent. That judgement is what stops you writing lab-only manifests in Phase 14.

PowerShell
docker ps --filter name=k3d-elastic-lab --format "table {{.Names}}\t{{.Image}}"
kubectl get deploy,ds -n kube-system
kubectl -n kube-system get helmchart traefik -o yaml | Select-String -Pattern "version|chart"
  • serverlb — an nginx container in front of the API server. Production has a real load balancer; the shape is the same, the thing is not.
  • traefik — a genuine ingress controller. Whatever production runs, the Ingress objects you write in Phase 05 are portable; the annotations are not.
  • local-path — hostPath volumes bound to one node. Production storage will be network-backed, which changes what happens when a node dies. Phase 04's whole point.

Two things to set before Phase 03

vm.max_map_count

Elasticsearch refuses to start unless the kernel allows at least 262144 memory-mapped areas, and the kernel here is the shared WSL2 VM — not the k3d containers. It resets on Docker Desktop restart, so expect to reapply it (or write it into %USERPROFILE%\.wslconfig).

PowerShell
wsl -d docker-desktop sysctl -w vm.max_map_count=262144
wsl -d docker-desktop sysctl vm.max_map_count   # confirm
Restart behaviour

k3d clusters survive a reboot but come back stopped. k3d cluster start elastic-lab brings them up; k3d cluster list shows what you have. Never delete when you meant stop — the data in local-path volumes goes with it.
