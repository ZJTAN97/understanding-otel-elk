Phase 04 · Topology

Three masters, two data nodes

Production runs a three-tier layout nobody currently justifies. This phase is where you earn the right to keep it — or to drop a tier on purpose.

Done when: five nodes hold the roles you declared, health is green, you have watched a shard relocate, and a production topology recommendation with its reasoning is written into learning-phases/18-production-design.md — provisional numbers included.

Snippets for

The tier question, answered as far as it can be

Production has -es-master, -es-ingest and -es-default. Two of those three tiers survive scrutiny.

TierVerdict
Dedicated master Keep, at 3. A master under query-heap pressure stalls cluster-state updates, and a stalled master is indistinguishable from a dead cluster justified
Dedicated ingest Drop. D4 puts enrichment in the OTel Collector, upstream. A tier whose job is running ingest pipelines you no longer write is a tier that idles inherited, not chosen
Data Keep, and give it the storage and heap the ingest tier was holding justified
Node count for production Blocked on Q2 — daily ingest volume and affordable node count lab runs regardless
ml / transform Off. Declaring node.roles is exhaustive, and each role costs memory revisit at Q7

Write that reasoning down in 18-production-design.md even while Q2 is open. A provisional recommendation with stated assumptions is reviewable; a blank section is how the current topology got inherited in the first place.

02

The manifest

Written to phase-4/k8s/elasticsearch.yaml. It supersedes the Phase 03 file; keep both in git so the diff is readable.

phase-4/k8s/elasticsearch.yaml · nodeSets only
  nodeSets:
    - name: master
      count: 3
      config:
        # Exhaustive. ml, transform and remote_cluster_client are now OFF.
        node.roles: ["master"]
        node.store.allow_mmap: false
      volumeClaimTemplates:
        - metadata: { name: elasticsearch-data }

      podTemplate:
        spec:
          containers:

              resources:

                - name: ES_JAVA_OPTS

    - name: data
      count: 2
      config:
        node.roles: ["data", "ingest"]

The nodeSet named default is gone

Applying this removes the default nodeSet. That is the rename exercise from step 06, happening for real, on your first apply — which is exactly why it is safe to do now: the cluster holds nothing yet. Note what it costs when empty, so you have a baseline for what it costs in step 06 when it is not.

03

Apply and watch the migration

PowerShell or zsh
kubectl apply -f phase-4/k8s/elasticsearch.yaml
kubectl get pods,es -n eck -w

The operator brings the new nodeSets up first, waits for the cluster to accept them, moves shards, and only then tears the old node down. Health dips and recovers; it should not go red. Keep the operator log open — the reconcile entries name each phase of this, and this is the one place in Part 1 where the operator is visibly doing something a StatefulSet could not do for itself.

PowerShell or zsh
kubectl get es obs -n eck -o jsonpath="{.status}"
kubectl get sts,pvc -n eck

Two StatefulSets now, five PVCs, and no trace of obs-es-default.

05

Replicas versus nodes, demonstrated

Create an index with a replica and put documents in it. An empty index relocates instantly and teaches you nothing; step 06 depends on there being something to move.

PowerShell
$ES = "https://localhost:9200"
$CA = "$env:TEMP\es-ca.crt"

curl.exe --cacert $CA -u "elastic:$PW" -X PUT "$ES/test-index" `
  -H "Content-Type: application/json" `
  -d '{\"settings\":{\"number_of_shards\":2,\"number_of_replicas\":1}}'

# a few thousand docs so relocation takes measurable time
1..2000 | ForEach-Object {
  curl.exe -s --cacert $CA -u "elastic:$PW" -X POST "$ES/test-index/_doc" `
    -H "Content-Type: application/json" -d "{\"n\":$_}" | Out-Null
}

curl.exe --cacert $CA -u "elastic:$PW" "$ES/_cat/shards/test-index?v"
zsh
ES=https://localhost:9200
CA=/tmp/es-ca.crt

curl --cacert $CA -u "elastic:$PW" -X PUT "$ES/test-index" \
  -H 'Content-Type: application/json' \
  -d '{"settings":{"number_of_shards":2,"number_of_replicas":1}}'

# a few thousand docs so relocation takes measurable time
for i in $(seq 1 2000); do
  curl -s --cacert $CA -u "elastic:$PW" -X POST "$ES/test-index/_doc" \
    -H 'Content-Type: application/json' -d "{\"n\":$i}" > /dev/null
done

curl --cacert $CA -u "elastic:$PW" "$ES/_cat/shards/test-index?v"

Four shards: two p, two r, and no primary sharing a node with its own replica. Now take a data node away and watch the consequence:

PowerShell or zsh
# edit phase-4/k8s/elasticsearch.yaml: nodeSet data count: 1
kubectl apply -f phase-4/k8s/elasticsearch.yaml
kubectl get es -n eck -w    # health → yellow

yellow, not red: every primary is still there, but the replicas have nowhere to go — a copy on the same node as its primary protects against nothing, so Elasticsearch refuses to allocate it. Set count back to 2 and it goes green again. This is the demonstration that a single-node lab cannot teach resilience, and the reason Phase 01 insisted on multiple agents.

06

The deliberate exercise: rename a nodeSet

With 2000 documents in place and count back at 2, change the nodeSet name from data to data-hot and apply.

PowerShell or zsh
kubectl apply -f phase-4/k8s/elasticsearch.yaml
kubectl get pods,pvc -n eck -w
✓obs-es-data-hot-0 and -1 appear as a new StatefulSet with new PVCs
✓Shards relocate off obs-es-data-* — watch _cat/shards show RELOCATING
✓Only once the data has moved does the old StatefulSet go away

Nothing in the diff says "migrate every byte of data." The nodeSet name is part of the StatefulSet name, the StatefulSet name is part of the PVC names, and Kubernetes cannot rename either — so ECK does the only correct thing available to it. In the lab that is thirty seconds. On a production data node it is hours of shard relocation, triggered by an edit that reads like a typo fix in review.

Carry this forward

Decide production's nodeSet names now, in Phase 18, and never touch them again. data-hot is a better name than data precisely because it survives the day someone adds a warm tier.

Three sharp edges

Anti-affinity is soft by default

ECK sets preferred, not required, pod anti-affinity within a nodeSet. On a three-node k3d cluster the scheduler will usually spread three masters across three nodes — but it is free to stack two on one node, and then a single node failure costs you quorum. Check with kubectl get pods -n eck -o wide. In production this belongs as requiredDuringSchedulingIgnoredDuringExecution across failure domains, which is a Phase 18 decision.

Never hand-edit voting exclusions

Scaling masters down is not a StatefulSet operation — a departing master must first be added to the voting configuration exclusions or the cluster can lose quorum mid-change. ECK does this for you on every nodeSet change. The failure mode to recognise is a master scale-down that appears stuck: that is usually the operator correctly waiting, not a hang. Reaching for _cluster/voting_config_exclusions by hand while the operator is mid-reconcile is how a healthy cluster becomes an unavailable one.

node.roles is exhaustive, and Kibana notices

Listing ["master"] does not mean "master, plus the defaults" — it means master and nothing else. With no node carrying ml or transform, the Kibana features that need them return errors rather than hiding themselves, and the error text names neither this file nor node roles. That is the right trade at this size, but write it in the Notes section now so the error is recognisable in Phase 13 rather than mysterious.
