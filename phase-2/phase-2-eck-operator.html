Phase 02 · ECK operator

Pinning ECK 3.0.0

The install method production used was fine. What was missing was a release record — so "we are on 2.13.0 and 3.x exists" stayed invisible for two years.

Done when: the operator pod is Running with a healthy reconcile loop, the chart version is pinned in a values file in git, and you can say out loud why kubectl get deploy -n elastic-system returns nothing.

The version question, answered

Step 1 of the phase doc asks you to pick the highest 3.0.x. I pulled helm.elastic.co/index.yaml and inspected the charts — here is what is actually published, and where the pin comes from.

FactFinding
Highest 3.0.x 3.0.0 — it is the only one. There is no 3.0.1. this is your pin
Also published 3.1.0, 3.2.0, 3.3.0–3.3.2, 3.4.0–3.4.1, 3.5.0 (latest) unsupported on 1.28
Chart guard kubeVersion: '>=1.21.0-0' on 3.0.0, 3.1.0 and 3.2.0 alike enforces nothing
Operator image docker.elastic.co/eck/eck-operator:3.0.0 → Phase 17 mirror
Helm on this machine not installed step 01
The guard you don't have

Every 3.x chart declares kubeVersion: '>=1.21.0-0'. So Helm will install 3.5.0 onto your 1.28 cluster without a word of complaint — and it will probably even come up. The 1.28 → ECK 3.0 boundary is Elastic's support matrix, enforced by nobody. That is precisely why the version has to be a tracked fact in a file: nothing in the tooling will catch the mistake for you.

Record 3.0.0 against Q6 and the ECK row of D3 in docs/00-decisions.md, which currently reads "Exact patch tag TBC". That is now answered.

03

Create the workload namespace first

managedNamespaces tells the operator what to watch; it does not create anything. Naming a namespace that does not exist gives you an operator that starts cleanly and reconciles nothing.

PowerShell or zsh — same command
kubectl create namespace eck
04

Install, pinned, from a values file

Already written to phase-2/helm/eck-operator/values.yaml. Every key below was checked against the 3.0.0 chart, not guessed from the docs.

phase-2/helm/eck-operator/values.yaml
# Restrict the operator to the workload namespace. Empty list = all namespaces.
# Does not create the namespace, and does not narrow RBAC while
# createClusterScopedResources is true — scoping is operator config, not RBAC.
managedNamespaces:
  - eck

# See the uninstall warning below before trusting this in production.
installCRDs: true

replicaCount: 1

image:
  repository: docker.elastic.co/eck/eck-operator
  # Defaults to appVersion; stated so it is greppable for the airgap mirror.
  tag: "3.0.0"
  pullPolicy: IfNotPresent

resources:
  limits:   { cpu: 1, memory: 1Gi }
  requests: { cpu: 100m, memory: 150Mi }

webhook:
  enabled: true
  manageCerts: true
  # Chart default. Fails OPEN — see the sharp edge below.
  failurePolicy: Ignore

telemetry:
  # No egress from the target environment.
  disabled: true

config:
  logVerbosity: "0"
PowerShell · from the repo root
helm install elastic-operator elastic/eck-operator `
  --namespace elastic-system --create-namespace `
  --version 3.0.0 `
  -f phase-2\helm\eck-operator\values.yaml

# the release record that production never had
helm list -n elastic-system
kubectl rollout status sts/elastic-operator -n elastic-system --timeout=180s
zsh · from the repo root
helm install elastic-operator elastic/eck-operator \
  --namespace elastic-system --create-namespace \
  --version 3.0.0 \
  -f phase-2/helm/eck-operator/values.yaml

# the release record that production never had
helm list -n elastic-system

--version is not optional

Omit it and Helm resolves to 3.5.0 today and something else next month. That single missing flag is the difference between this install and the one you are replacing. Do a --dry-run first if you want to read the rendered objects before they land.

✓One StatefulSet, one pod, one Service, a ConfigMap and a Secret
✓Ten CRDs: elasticsearch, kibana, apmserver, beat, agent, logstash, enterprisesearch, elasticmapsserver, stackconfigpolicy, elasticsearchautoscaler

That last one is worth sitting with. createClusterScopedResources defaults to true, so the operator holds cluster-wide RBAC and simply chooses to watch one namespace, because scoping is passed as operator config. Flip it to false and the chart emits per-namespace Role/RoleBinding instead — real least-privilege, and a decision to make deliberately in Phase 18.

06

Watch it think

Leave this running in a second terminal for the rest of Part 1. Watching reconciliation as you apply manifests is the fastest way to build the mental model.

PowerShell or zsh · second terminal
kubectl logs -n elastic-system sts/elastic-operator -f

A healthy idle loop is quiet: "accepting leadership" at startup, then periodic reconcile entries with "iteration" and a namespace. Errors mentioning certificate in the first thirty seconds are the operator minting its own webhook certs and are expected.

07

The deliberate exercise: make the webhook talk to you

Apply a resource with a version that does not exist. The rejection does not come from the API server or from Elasticsearch — nothing has been created yet.

PowerShell
@'
apiVersion: elasticsearch.k8s.elastic.co/v1
kind: Elasticsearch
metadata:
  name: bogus
  namespace: eck
spec:
  version: 9.99.0
  nodeSets:
  - name: default
    count: 1
'@ | kubectl apply -f -
zsh
kubectl apply -f - <<'EOF'
apiVersion: elasticsearch.k8s.elastic.co/v1
kind: Elasticsearch
metadata:
  name: bogus
  namespace: eck
spec:
  version: 9.99.0
  nodeSets:
  - name: default
    count: 1
EOF

Quote the delimiter (<<'EOF'). Unquoted, zsh expands $ and backticks inside the manifest.

Error from server (Forbidden): error when creating "STDIN":
admission webhook "elastic-es-validation-v1.k8s.elastic.co" denied the request:
Elasticsearch.elasticsearch.k8s.elastic.co "bogus" is invalid:
spec.version: Invalid value: "9.99.0": Unsupported version

The webhook name in that message is the component you just installed. Now do the same thing with nodeSets: [], or two nodeSets sharing a name, and read those messages too — this is the validation you get for free, and the reason a broken webhook is worse than no webhook.

Two sharp edges the phase doc understates

The webhook fails open, not closed

The doc says a webhook left behind without its operator makes kubectl apply "hang or be rejected". With the chart default failurePolicy: Ignore, the opposite happens: after a ~10 second timeout per request, admission is allowed through unvalidated. Quieter and arguably worse — invalid specs reach a cluster with nothing running to reconcile them. Set failurePolicy: Fail and the doc's description becomes literally true, cluster-wide, for every Elastic resource. Know which one production has before anyone touches elastic-system.

helm uninstall deletes your data

With installCRDs: true, the CRDs are ordinary templates from the bundled eck-operator-crds subchart — so they are part of the release, and helm uninstall elastic-operator removes them. Deleting a CRD deletes every object of that kind: every Elasticsearch, in every namespace, in one command. Elastic's own values file warns about this. For production, split it:

the production shape, for Phase 18
helm install eck-crds elastic/eck-operator-crds --version 3.0.0
helm install elastic-operator elastic/eck-operator --version 3.0.0 `
  --set installCRDs=false -f values.yaml
the production shape, for Phase 18
helm install eck-crds elastic/eck-operator-crds --version 3.0.0
helm install elastic-operator elastic/eck-operator --version 3.0.0 \
  --set installCRDs=false -f values.yaml

In the lab, keep installCRDs: true — you want teardown to be one command. Just know which behaviour you signed up for.
