Phase 03 · First Elasticsearch

One node, forty objects

Twenty lines of YAML. The work of this phase is enumerating everything those twenty lines generate — once, deliberately — so that nothing in production is a mystery.

Done when: kubectl get es -n eck reports green and Ready, you can name every Secret, Service and workload the operator created and say what it is for, and you have queried the cluster with full certificate validation — no -k.

Snippets for

The namespace question, answered

The phase doc puts this cluster in elastic-stack. Phase 02 installed an operator whose managedNamespaces is [eck]. Those two facts do not fit together, and the failure they produce is silent.

FactFinding
Phase doc says namespace: elastic-stack stale — predates Phase 02
Operator watches managedNamespaces: [eck], from phase-2/helm/eck-operator/values.yaml this is the one that binds
Webhook checks the spec — version, nodeSets, names. Not where you put it accepts both
Elasticsearch version 8.19.21 — 00-decisions.md D3 Kibana must match exactly
Storage class local-path — k3d ships the Rancher provisioner node-local, see below
Reconciled by nobody

Apply into an unwatched namespace and everything looks fine: the webhook is cluster-scoped, so it validates the spec and admits the object. Then nothing happens. No StatefulSet, no pod, no events, and kubectl get es shows a row whose HEALTH and PHASE columns stay empty forever. That blank-columns-plus- no-events fingerprint means no operator is watching — it is not a slow start. Use eck, or add the namespace to managedNamespaces and helm upgrade. Do not do both halves of the decision by accident.

What twenty lines generate

Run it

01

Decide the mmap question before you apply

Elasticsearch memory-maps index files and wants vm.max_map_count=262144. That sysctl belongs to the kernel your Docker Desktop VM is running — not to the k3d containers, and not to macOS or Windows. You have two ways out, and they are not equal.

PowerShell · the docker-desktop WSL distro
wsl -d docker-desktop sysctl vm.max_map_count           # check first
wsl -d docker-desktop sysctl -w vm.max_map_count=262144
zsh · the LinuxKit VM, entered via a privileged container
docker run --rm --privileged --pid=host alpine \
  nsenter -t 1 -m -u -n -i sysctl vm.max_map_count          # check first
docker run --rm --privileged --pid=host alpine \
  nsenter -t 1 -m -u -n -i sysctl -w vm.max_map_count=262144

Neither survives a Docker Desktop restart, so you would be re-running it for the next seventeen phases. The manifest below instead sets node.store.allow_mmap: false, which makes the requirement go away at a search-performance cost — right for a laptop, wrong for production, where you set the sysctl on the nodes and delete the line. Pick one. The old k3d-plan.md did both, which is belt and braces on a cluster with no trousers.

02

The manifest

Already written to phase-3/k8s/elasticsearch.yaml. Three of these lines are worth understanding rather than copying; they are the commented ones.

phase-3/k8s/elasticsearch.yaml
apiVersion: elasticsearch.k8s.elastic.co/v1
kind: Elasticsearch
metadata:
  name: obs
  # The namespace the Phase 02 operator actually watches.
  namespace: eck
spec:
  version: 8.19.21
  nodeSets:
    - name: default
      count: 1
      config:
        # Lab only. In production set the sysctl and delete this.
        node.store.allow_mmap: false
      volumeClaimTemplates:
        - metadata:
            # This name is required. Anything else is mounted as an extra
            # volume and the data path silently stays on the 1Gi default.
            name: elasticsearch-data
          spec:
            accessModes: [ReadWriteOnce]
            resources:
              requests:
                storage: 10Gi
            storageClassName: local-path
      podTemplate:
        spec:
          containers:
            - name: elasticsearch
              resources:
                requests:
                  memory: 2Gi
                  cpu: 1
                limits:
                  # No cpu limit on purpose: CFS throttling during
                  # recovery and merges costs more than it protects.
                  memory: 2Gi
              env:
                # Heap = half the limit. The rest is off-heap and page
                # cache. Keep Xms == Xmx.
                - name: ES_JAVA_OPTS
                  value: "-Xms1g -Xmx1g"

Omitting volumeClaimTemplates entirely is legal and gives you a 1Gi claim. Declaring it means you will notice when it needs to change — and Phase 06 has a lesson about what happens to these volumes when you edit them.

03

Apply, and watch two things at once

PowerShell or zsh — same commands
kubectl apply -f phase-3/k8s/elasticsearch.yaml
kubectl get elasticsearch -n eck -w      # `es` is the short name

The HEALTH column walks unknown → red → green; PHASE goes ApplyingChanges → Ready. Two to three minutes on a first run, most of it pulling the image. Keep the operator log from Phase 02 open in the second terminal while this happens — the reconcile entries are the narration for what you are watching.

If it stalls in Pending

kubectl describe pod -n eck obs-es-default-0 first, always. Insufficient memory means the 2Gi request does not fit a k3d agent — raise Docker Desktop's memory allocation, not the manifest. A pod stuck on waiting for first consumer is normal for local-path: the PVC binds only once the pod is scheduled.

05

Connect properly, with certificate validation

Port-forward in one terminal and leave it:

PowerShell or zsh · second terminal
kubectl port-forward -n eck service/obs-es-http 9200

The lazy way — curl -k — works, and teaches nothing. Do it once the right way, because this is the exact mechanism the Collector will use in Phase 08.

PowerShell
$PW = kubectl get secret obs-es-elastic-user -n eck `
  -o go-template='{{.data.elastic | base64decode}}'

# Pipe to Set-Content, never redirect. PowerShell 5.1 redirection
# writes UTF-16LE and curl then rejects the PEM: "no start line".
kubectl get secret obs-es-http-certs-public -n eck `
  -o go-template='{{index .data "ca.crt" | base64decode}}' `
  | Set-Content -Encoding ascii $env:TEMP\es-ca.crt

# curl.exe, not curl — bare `curl` is an alias for Invoke-WebRequest
# --resolve, because the cert has no `localhost` SAN. See below.
curl.exe --cacert $env:TEMP\es-ca.crt `
  --resolve obs-es-http.eck.svc:9200:127.0.0.1 `
  -u "elastic:$PW" https://obs-es-http.eck.svc:9200
zsh
PW=$(kubectl get secret obs-es-elastic-user -n eck \
  -o go-template='{{.data.elastic | base64decode}}')

kubectl get secret obs-es-http-certs-public -n eck \
  -o go-template='{{index .data "ca.crt" | base64decode}}' > /tmp/es-ca.crt

# no -k anywhere; --resolve because the cert has no `localhost` SAN
curl --cacert /tmp/es-ca.crt \
  --resolve obs-es-http.eck.svc:9200:127.0.0.1 \
  -u "elastic:$PW" https://obs-es-http.eck.svc:9200
✓A JSON banner with "number" : "8.19.21" and "cluster_name" : "obs"
✓No certificate warning, because you supplied the CA rather than ignoring it
Why not https://localhost:9200

Supplying the CA only settles who signed the certificate. TLS also checks that the name you dialled appears in the certificate's Subject Alternative Names, and the operator mints in-cluster names only:

kubectl get secret obs-es-http-certs-public -n eck \
  -o go-template='{{index .data "tls.crt" | base64decode}}' \
  | openssl x509 -noout -text | grep -A2 "Alternative Name"

DNS:obs-es-http, DNS:obs-es-http.eck, DNS:obs-es-http.eck.svc, ...

No localhost, no 127.0.0.1 — so curl --cacert … https://localhost:9200 fails with SSL: no alternative certificate subject name matches target host name 'localhost'. --resolve is the fix: dial a name the certificate actually claims, and point that name at the port-forward. Verification stays fully on.

The other fix is spec.http.tls.selfSignedCertificate.subjectAltNames, adding localhost to the cert itself. It works, and it bakes a laptop artifact into a manifest that is supposed to describe the cluster. Keep it client-side.

Then ask the cluster how it feels:

PowerShell
$ES = "https://obs-es-http.eck.svc:9200"
$RESOLVE = "obs-es-http.eck.svc:9200:127.0.0.1"

curl.exe --cacert $env:TEMP\es-ca.crt --resolve $RESOLVE -u "elastic:$PW" `
  "$ES/_cluster/health?pretty"
curl.exe --cacert $env:TEMP\es-ca.crt --resolve $RESOLVE -u "elastic:$PW" `
  "$ES/_cat/nodes?v"
zsh
ES=https://obs-es-http.eck.svc:9200
RESOLVE=obs-es-http.eck.svc:9200:127.0.0.1

curl --cacert /tmp/es-ca.crt --resolve $RESOLVE -u "elastic:$PW" \

06

The deliberate exercise: find the controller boundary

Delete the pod and watch carefully. The question is not "does it come back" — it is who brought it back.

PowerShell or zsh
kubectl delete pod obs-es-default-0 -n eck
kubectl get pod,es -n eck -w

The StatefulSet controller recreated the pod — that is stock Kubernetes, and it would have happened with the operator scaled to zero. The ECK operator only observed the result and updated HEALTH on the Elasticsearch object. The pod reattached to the same PVC, so no data moved. Knowing exactly where that line sits is worth more than any amount of documentation, because it tells you which component to suspect when a pod does not come back.

Your port-forward died with the pod. That is expected; restart it.

Three sharp edges

Green here does not mean resilient

A single node reports green only because the system indices use auto_expand_replicas and quietly settle at zero replicas. The first index you create with number_of_replicas: 1 goes yellow and stays there — nothing is wrong, there is simply nowhere to put a copy. Do not train yourself to read green as "safe" on this cluster; it currently means "one copy of everything, on one disk."

local-path pins your data to one node

The Rancher provisioner writes to a directory on whichever k3d node scheduled the pod, and the PVC keeps it pinned there. Cordon that node and the pod will not reschedule — it will sit Pending forever rather than move. It is a faithful stand-in for production's local-disk storage class, which behaves the same way, and it is why Phase 04's node roles and Phase 07's snapshots exist.

Deleting the Elasticsearch deletes the data too

spec.volumeClaimDeletePolicy defaults to DeleteOnScaledownAndClusterDeletion, so kubectl delete es obs -n eck takes the PVCs — and the data — with it. That is the operator doing it, not Kubernetes: a StatefulSet on its own always leaves its PVCs behind. Set DeleteOnScaledownOnly if you want a deleted cluster's volumes to survive, and check kubectl get pvc -n eck after any teardown either way.
