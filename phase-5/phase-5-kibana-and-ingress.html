Phase 05 · Kibana, associations, Ingress

Associations and the 502

Two lines of elasticsearchRef replace a credential-handling project. Then an ingress puts a hostname in front of it, and teaches you the most misleading error in the stack.

Done when: Kibana loads at kibana.lab.local through Traefik — not a port-forward — you can recite the five things elasticsearchRef caused, and you have seen the 502 and read the log line that explains it.

What this phase needs that you do not have yet

The phase doc says "k3d ships Traefik" and moves on. Traefik is there; a way to reach it is not. phase-1/k3d/cluster.yaml declares no ports:, so the k3d load balancer publishes nothing to the host and an Ingress is unreachable no matter how correct it is.

FactFinding
Traefik Installed by k3s as a HelmChart, ingressClassName: traefik already running
Host ports None. cluster.yaml has no ports: block fix in step 01
Traefik version k3s 1.28 ships v2.10 → CRDs under traefik.containo.us v3 uses traefik.io
Backend protocol Set on the Service via annotations, not on the Ingress the 502
Memory Kibana adds 1Gi on top of Phase 04's 7Gi 8Gi is now the floor

The two things worth understanding

Run it

01

Publish a host port to the k3d load balancer

An Ingress with nothing listening on the host is a YAML exercise. k3d cluster edit adds the mapping in place — it recreates only the load balancer container, so the five Elasticsearch pods and their PVCs are untouched.

PowerShell or zsh
k3d cluster edit elastic-lab --port-add "8081:80@loadbalancer"

docker ps --filter name=k3d-elastic-lab-serverlb   # 0.0.0.0:8081->80/tcp
kubectl get pods -n eck                            # still Running, unchanged

Then fold the same mapping into phase-1/k3d/cluster.yaml, so the next cluster you build from scratch has it:

phase-1/k3d/cluster.yaml · add
ports:
  - port: "8081:80"
    nodeFilters: [loadbalancer]

Port 80 on the host is often already taken and needs privileges; 8081 avoids both arguments. Traefik matches Host() without the port, so name-based routing works exactly as it would on 80.

Memory, again

Kibana's 1Gi lands on top of Phase 04's 7Gi. If Docker Desktop is at 8Gi you are now at the edge — drop the master nodeSet to count: 1 for this phase if pods start going Pending, and put it back for Phase 06, which needs the quorum.

02

Add a hostname your machine can resolve

PowerShell · as Administrator
Add-Content -Path $env:SystemRoot\System32\drivers\etc\hosts `
  -Value "127.0.0.1 kibana.lab.local"

ping kibana.lab.local   # 127.0.0.1
zsh
sudo sh -c 'echo "127.0.0.1 kibana.lab.local" >> /etc/hosts'

ping -c1 kibana.lab.local   # 127.0.0.1

A hosts entry rather than localhost is the point: you are exercising name-based virtual hosting, which is what production's kibana-ingress and apm-ingress actually do.

03

Deploy Kibana

Written to phase-5/k8s/kibana.yaml.

phase-5/k8s/kibana.yaml
apiVersion: kibana.k8s.elastic.co/v1
kind: Kibana
metadata:
  name: obs
  namespace: eck
spec:
  # Must match Elasticsearch exactly. Skew is refused, not tolerated.
  version: 8.19.21
  count: 1

  # The entire phase is in these two lines.
  elasticsearchRef:
    name: obs

  http:
    service:
      metadata:
        annotations:
          # Traefik reads these off the SERVICE, not the Ingress.
          traefik.ingress.kubernetes.io/service.serversscheme: https
          traefik.ingress.kubernetes.io/service.serverstransport: eck-kibana-tls@kubernetescrd

  podTemplate:
    spec:
      containers:
        - name: kibana
          resources:
            requests: { memory: 1Gi, cpu: 500m }
            limits:   { memory: 1Gi }
          env:
            # Kibana is Node.js. Without this the heap sizes itself
            # against the host and gets OOMKilled at a 1Gi limit.
            - name: NODE_OPTIONS
              value: "--max-old-space-size=800"

Apply it with the service annotations still in place, but before the Ingress exists. Step 06 is the deliberate exercise and needs them removed — it is cleaner to take a working config apart than to guess at a broken one.

PowerShell or zsh
kubectl apply -f phase-5/k8s/kibana.yaml
kubectl get kibana -n eck -w      # HEALTH green, ~90s
04

Inspect what the association created

PowerShell
kubectl get kibana obs -n eck -o jsonpath="{.status.associationStatus}"
kubectl get secret -n eck | Select-String -Pattern "kibana|kb-"
zsh
kubectl get kibana obs -n eck -o jsonpath='{.status.associationStatus}'
kubectl get secret -n eck | grep -E "kibana|kb-"
✓Established — the one field to check when two Elastic resources will not talk
✓A user secret, a copy of the Elasticsearch CA, and an association-config secret

Now ask Elasticsearch who that user is. The username is generated from the namespace and both resource names — it is not elastic, and it is not a name anyone typed:

PowerShell · port-forward 9200 in a second terminal
# --resolve as in Phase 03: the cert has no `localhost` SAN
$ES = "https://obs-es-http.eck.svc:9200"
$RESOLVE = "obs-es-http.eck.svc:9200:127.0.0.1"

curl.exe --cacert $env:TEMP\es-ca.crt --resolve $RESOLVE -u "elastic:$PW" `
  "$ES/_security/user?pretty"
zsh · port-forward 9200 in a second terminal
# --resolve as in Phase 03: the cert has no `localhost` SAN
ES=https://obs-es-http.eck.svc:9200
RESOLVE=obs-es-http.eck.svc:9200:127.0.0.1

curl --cacert /tmp/es-ca.crt --resolve $RESOLVE -u "elastic:$PW" \
  "$ES/_security/user?pretty"

Least privilege, applied automatically, with rotation — the thing you would otherwise be writing a runbook for. This is also the mechanism the Collector will lean on in Phase 08.

05

Reach it the quick way, then the real way

PowerShell or zsh
kubectl port-forward -n eck service/obs-kb-http 5601
# https://localhost:5601 — user elastic, password from Phase 03.
# Certificate warning expected: this is the ECK self-signed cert.

That proves Kibana works. Now stop it and go through the ingress, which is the configuration production actually runs. Check the CRD group first — it differs between Traefik v2 and v3, and applying the wrong one fails with no matches for kind:

PowerShell
kubectl get crd | Select-String serverstransport
# traefik.containo.us -> v2.x, matches the file as written
# traefik.io          -> v3.x, edit apiVersion first

kubectl apply -f phase-5\k8s\ingress.yaml
kubectl get ingress,serverstransport -n eck
zsh
kubectl get crd | grep serverstransport
# traefik.containo.us -> v2.x, matches the file as written
# traefik.io          -> v3.x, edit apiVersion first

kubectl apply -f phase-5/k8s/ingress.yaml
kubectl get ingress,serverstransport -n eck
phase-5/k8s/ingress.yaml
apiVersion: traefik.containo.us/v1alpha1
kind: ServersTransport
metadata:
  name: kibana-tls
  namespace: eck
spec:
  # A SAN on the ECK certificate. Traefik dials the pod IP, so without
  # this the hostname check fails even though the CA is trusted.
  serverName: obs-kb-http.eck.svc
  rootCAsSecrets:
    - obs-kb-http-certs-public
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: kibana
  namespace: eck
  annotations:
    traefik.ingress.kubernetes.io/router.entrypoints: web
spec:
  ingressClassName: traefik
  rules:
    - host: kibana.lab.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: obs-kb-http
                port: { number: 5601 }
✓http://kibana.lab.local:8081 loads the login page with no port-forward running

Note what the ingress is not doing: no credentials, no CA, no mention of Elasticsearch. It routes a hostname to a Service, and everything behind that was arranged by the association.

Why the browser hop is plain HTTP here

Deliberate scope control. A trusted browser certificate means a local CA and an OS trust store — a real task, but a different one, and it would bury the lesson this phase is actually about. Production terminates a proper certificate at the ingress; that belongs in Phase 18, alongside the decision about which CA issues it in an air-gapped environment.

06

The deliberate exercise: break the backend protocol

You have a working path. Take out the one annotation that makes it work and watch how badly the symptom describes the cause.

PowerShell or zsh
# delete the two annotations under spec.http.service.metadata, then:
kubectl apply -f phase-5/k8s/kibana.yaml

# reload http://kibana.lab.local:8081 → 502 Bad Gateway
kubectl logs -n eck -l kibana.k8s.elastic.co/name=obs --tail=30
{"log.level":"error","message":"{ code: 'ERR_SSL_HTTP_REQUEST',
  reason: 'http request', ... }"}
# or, depending on build:
4A7C0000:error:0A00010B:SSL routines:ssl3_get_record:wrong version number

Kibana is healthy. Elasticsearch is healthy. The association is Established. The browser says 502, which reads as "the backend is down", and the pod list agrees that nothing is down. The only honest evidence is that log line — and you only think to look at it if you have seen this once before. That is the entire value of doing it on purpose now. Put the annotations back and confirm it recovers.

The shortcut, and its price

You can instead set spec.http.tls.selfSignedCertificate.disabled: true on the Kibana resource and let the ingress talk plain HTTP to the pod. It is one line and it works. It also means Kibana traffic crosses the cluster network unencrypted — including the session cookie of every admin who logs in. A defensible choice only where pod-to-pod traffic is already covered by something else; write down which it is before choosing it.

Three sharp edges

The saved-objects encryption key lives in a Secret you can delete

ECK generates the key that encrypts alerting rules, connectors and other saved objects, and keeps it in the Kibana config Secret. Delete the Kibana resource and that Secret goes with it; recreate Kibana and a new key is generated, at which point every encrypted saved object created before is unreadable — Kibana reports decryption errors, not a missing key. Nothing is lost today because Phase 13 has not created anything yet. Before it does, decide where that key is backed up, and note it as a Phase 19 cutover input.

Annotate the Service through the CR, never with kubectl

obs-kb-http is operator-managed. kubectl annotate on it survives until the next reconcile and then quietly disappears, which produces a 502 that reappears hours after someone "fixed" it. spec.http.service.metadata.annotations is the supported way in, and it is declarative, which is the point of this whole repo.

Cross-namespace associations do not work by default

elasticsearchRef takes an optional namespace, but the operator refuses cross-namespace references unless it was installed with them enabled. Everything here is in eck, so it does not bite — it bites in Phase 18 if production splits Kibana and Elasticsearch across namespaces. The symptom is an associationStatus that never leaves Pending.
